# 持续维护工作流

维护分为三项独立工作：链接可访问、来源仍支持具体主张、网站与离线版正常工作。任何一项通过都不能替代另外两项。

## 固定节奏

| 周期 | 工作 | 留下的结果 |
|---|---|---|
| 每周一 | 查看 External link report；复核高变动官方来源的公告；处理维护队列 | 变更／无变更／无法核验的明确记录 |
| 每周 | 按队列轮查正文与清单，检查未登记的年份、金额、期限、地区限制 | 现有80份文件八周轮完；新风险加入台账 |
| 每14天 | 旅行与移民动态范围完整复核 | 有适用身份、地区、生效日期的证据记录 |
| 每30天 | 税务、福利、医保、疫苗筛查等登记范围复核 | 更新主张、来源或范围限制 |
| 每90天 | 急救指引完整复核；阅读体验与导出抽查 | 官方专业指引记录；手机／桌面／离线阅读检查 |
| 每年10月至次年1月 | 逐项检查下一年度税额、福利限额、表格、参保材料 | 区分公布年度、适用年度与生效日期，保留仍适用的旧年度信息 |
| 发现重大变化时 | 优先处理可能影响安全、身份、费用或截止期的内容 | 尽快修订；未能确认时明确标注待核范围 |

这些周期是本项目的编辑安排，不是官方规定。来源有重大公告时不等到例行日期。旅行还须按具体行程重新核对。

## 台账与证据

`maintenance/review-registry.json` 保存11个初始范围及正文已引用的官方／专业来源入口。入口是待检查集合，不表示每个入口都支持范围内所有主张。首次建档未把旧章末日期迁移为整项核验；`last_verified: null` 表示尚未建立该范围的证据基线，并不表示正文已发现错误。首次完成目标为2026-10-01。

每次执行：

1. 运行 `python scripts/maintenance_report.py`；在 Actions 的 Editorial maintenance queue 下载JSON和Markdown队列。报告只安排任务，不修改正文。
2. 读取范围内的具体句子和原始官方页面；按身份、地区、年度逐条比较。检查原文注释、例外、发布与生效日期；页面更新时间不是规则生效日。
3. 在 `maintenance/reviews/YYYY-MM-DD-topic.md` 按下方模板记录。无需修改也要说明实际核过哪些主张；不能只写“无变化”。页面403、无法读取或来源冲突时记录缺口，不能算核验完成。
4. 完整覆盖登记范围后，才更新该条目的 `last_verified` 与 `review_record`。部分完成则保持日期，或拆出已完成的更小范围。自动脚本只校验记录文件存在，证据质量仍须编辑审阅。
5. 更新正文和关联清单，按 [主题维护表](topic-maintenance.md) 检查所有复用处；新增范围要加稳定ID、文件、来源、周期和首次截止日。

证据记录模板：

```markdown
# 日期 / 范围ID
- 执行者：
- 结果：确认原文 / 已修订 / 部分核验 / 无法核验
- 正文文件与小节：
- 逐条主张（原文 → 建议修订，或原文仍成立的依据）：
- 适用身份、司法辖区、年度、例外：
- 来源URL及支持主张的具体位置：
- 来源公布日期 / 规则生效日期 / 本次访问日期：
- 已检查的范围 / 未决缺口：
- 关联正文、清单与搜索入口：
- 验证结果 / 修订提交或PR：
```

## 链接处理

External link report 每周一13:17 UTC和相关文件变化时运行。404／410为明确断链；限流、403和暂时故障分别处理，不能一律删除。重试后找原机构的新入口，阅读新页面确认支持同一主张，再替换。禁止仅为了“绿灯”把所有深链接换成机构首页。重定向仍应检查语义，PDF／表格还要比较版本。

维护队列每周一13:47 UTC运行，保留90天报告；外链报告保留30天。GitHub计划任务可能延迟；长期无活动可能停用，缺失报告时从 Actions 手动运行并检查调度状态。报告之间不是串行依赖，应查看各自日期，不能把上周外链结果当本周结果。

## 修订与发布

在维护分支提出修改，使用证据记录供审阅。合并前按 [站点维护](site-maintenance.md) 运行构建与回归检查。标题变动检查旧链接；内容修改检查关联清单；UI变动检查桌面与手机；导出变动抽看中文PDF和真实阅读器。

合并main会触发网站与离线版共同部署。检查Actions成功后再看线上受影响页面与下载清单。普通维护不会自动创建新的GitHub Release；正式版本需同时修改VERSION和版本说明，并遵循现有 `Release v...` 提交约定。出现部署失败先核对线上实际版本，不宣称发布成功。回退采用revert提交，保留审计历史。

## 下一阶段改进顺序

1. 完成初始11项证据基线，优先移民／旅行、医保期限、下一年度税务福利数值；再把宽范围拆成可独立核验的主张。
2. 增加PR合并前完整构建门禁，覆盖网站、内部路由和所有导出；目前main部署检查不能替代合并前检查。
3. 在读者页面展示“具体核验范围／日期／仍有缺口”，避免全章一个日期造成全量背书；保留可查看的勘误记录。
4. 补真实手机、PDF打印和EPUB阅读器体验；记录字体、目录、表格和跨页问题。
5. 建立官方公告或页面变化提醒。内容差异只用于触发人工复核，不自动改写医疗、法律、税务结论。
